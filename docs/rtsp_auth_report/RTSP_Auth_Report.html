2. Flow overview

① POST /authorize
(get challenge)→ ② POST /authorize
(send signature → token)→ ③ PUT /keepalive
every 22 s→ ④ POST StartVideo
(per camera → RTSP URL)→ ⑤ open rtsp://…?token=
in FFmpeg/OpenCV

Steps ①–③ run once per DVR in the token server. Step ④ runs per camera on each worker. Base URL for every call: https://<server>/admin/API/. The token server and classification skip TLS certificate checks (verify=False); detection's StartVideo call uses normal certificate checks.

3. Camview DVR APIs

① Login, step 1: get challenge

POST https://dXX.camview.io/admin/API/accounts/authorize
Content-Type: application/json

{ "userName": "system", "ipAddress": "", "clientType": "WINPC_V1" }

Response (HTTP 401 or 200) gives realm, randomKey, publickey, plus a Set-Cookie header that must go back in step 2.

② Login, step 2: send signature, get token

Signature is a five-round MD5 chain:

t1 = md5(password)
t2 = md5(user + t1)
t3 = md5(t2)
t4 = md5(user + ":" + realm + ":" + t3)
signature = md5(t4 + ":" + randomKey)
POST https://dXX.camview.io/admin/API/accounts/authorize
Content-Type: application/json
Cookie: <Set-Cookie from step 1>

{ "mac": "", "signature": "<signature>", "userName": "system",
  "randomKey": "<randomKey>", "publicKey": "<publickey>",
  "encryptType": "MD5", "ipAddress": "", "clientType": "WINPC_V1", "userType": "0" }

Response: {"token": "..."}. This is the session token.

Error codeMeaningWhat the code does
1101MD5 rejected (needed for d15)gets a fresh challenge and retries with "encryptType": "RSA"
2002account locked (unlockRemainTime in response)stops; token server waits 400 s before trying again (lockout is ~300 s)

③ Keepalive

PUT https://dXX.camview.io/admin/API/accounts/keepalive
Content-Type: application/json
X-Subject-Token: <session token>

{}

Sent every 22 s. 200 = session alive. 401 = session gone, token dropped, next request logs in again.

④ StartVideo: get the RTSP URL for one camera

POST https://dXX.camview.io/admin/API/MTS/Video/StartVideo?token=<session token>
Content-Type: application/json;charset=UTF-8
X-Subject-Token: <session token>

{ "clientType": "WINPC_V1", "project": "PSDK", "method": "MTS.Video.StartVideo",
  "data": {
    "streamType": "1",
    "optional": "/admin/API/MTS/Video/StartVideo?token=<session token>",
    "channelId": "<device_id>$1$0$<camera_no>",
    "dataType": "2",
    "enableRtsps": "0"
  } }
  • device_id and camera_no come from the camera_links_rtsp row.
  • Response data.url (and data.url2) can hold several URLs joined by |. The code splits them; detection also drops URLs whose port is not reachable.
  • Response data.token is the stream token (falls back to the session token if missing).
  • 401 here means the session token is dead: the worker reports it to the token server (/evict) and fetches a new one. Classification first checks the 401 body, because some firmware returns stream data with a 401.
  • Detection caches the result per camera for 180 s (STARTVIDEO_CACHE_TTL).

⑤ Final RTSP URL

rtsp://<host>:<port>/<path from data.url>?token=<stream token>

No username/password goes into the RTSP URL itself; the token is the only auth.

4. Token server (internal API)

scripts/detection/camview_token_server.py runs on worker-0 (192.168.19.30), port 8090 under pm2 as camview-token-server (online, checked today). It is the only process that logs in to the DVRs; every worker asks it for the token.

6. Things to watch

  • Debug scripts (dss_stream.py, fetch_rtsp_url.py, test_camera_frame_capture.py, test_rtsp_from_excel.py) do not load .env and have the old password hard-coded, so their login now fails (test_camera_frame_capture.py uses CAMVIEW_AUTH_PASS only if it is exported in the shell). Repeated failed logins can lock the shared system account on that DVR for the whole fleet. Update them to read .env before using them. With the right password, a direct login would instead kill the shared session and every worker would get 401 until the token server logs in again.
  • Repeated bad logins lock the system account for ~5 min (code 2002) on that DVR.
  • Only the token server (worker-0) logs in, so a password change takes effect after updating script-server/.env on worker-0 and running pm2 restart camview-token-server. Keep .env on the other workers in sync too, for the direct-login fallback.
