1Overview

The platform monitors examination centre cameras during each shift and detects events such as a mobile phone in a lab, a crowd at the entry gate or unauthorised presence in the server room. Each event is saved with an annotated snapshot. Every detection is reviewed by a CDIS analyst before it is released, so only verified alerts reach the client dashboard and the observers' mobile phones.

Processing stages

  1. Connectivity checkEach camera is opened over its RTSP or HLS link. Cameras that cannot be reached are marked Not Accessible and excluded from analysis.
  2. View classificationAn AI model assigns each accessible camera a view type (Computer Lab, Server Room, Entry, Outside and so on), so that each analytic runs only on the camera types it applies to.
  3. Detection during the shiftOnly the analytics scheduled for the shift run, on the camera types and within the time windows defined in the analytics plan.
  4. Analyst reviewDetections are verified by CDIS analysts. Verified detections are released to the client Detections page.
  5. Client actionThe client accepts a valid alert, which triggers an SMS to the designated observers, or removes a false alert. No detection is deleted, and removals remain available for review.
  6. ReportingA per-shift Excel report lists camera status and every detection with a link to its image.

3Setup timeline

The sequence below reflects the recommended lead times. Exact dates are confirmed with your CDIS coordinator.

Before the first examination day

  • Submit Files 1 to 7 and the user list. Every upload is validated and, if incorrect, rejected with row-level messages, so allow time for corrections.
  • CDIS creates the examination and shifts, loads the schedules and cameras, and registers the SMS templates.
  • CDIS runs a scene classification and a connectivity check, then shares the list of cameras that are Not Accessible or Uncertain so that they can be corrected before the examination.
  • Users register and are verified (see Section 6).
  • CDIS assigns the verified users named in the user list to the examination, which gives them access to it on the client dashboard.
  • CDIS schedules the analytics from the submitted plan and confirms the timings with the client.

On each examination day

  • Approximately two hours before a shift: scene classification and connectivity check of that shift's cameras.
  • Before the shift starts: tamper, inversion and entry/exit checks begin.
  • During the shift: in-room analytics (phone, proximity, invigilator, crowd, server room) run for the duration of the shift.
  • The client accepts or removes alerts as they arrive and downloads the shift report afterwards.
  • If a schedule changes during the examination, the corrected file replaces the previous one and takes effect from the next launch of that shift's job. For camera list changes (new links, moved or removed cameras), inform CDIS: new cameras are added on upload, and changes to existing cameras are applied by CDIS.

4File specifications

Each file must be submitted in exactly the format shown below. These formats are identical to the blank templates supplied by CDIS with this guide, and header names must match them character for character. Files that deviate are rejected at upload or need manual re-entry by CDIS. Columns marked with a green underline are read by the system; the remaining columns are informational and may be left empty. Each example provides a Copy header row button for pasting into row 1 of a new sheet.

Column required or read by the system

General requirements for all Excel files

  • Accepted file types: .xlsx, .xls and .ods. Maximum size: 10 MB.
  • Only the first sheet of a workbook is read. If a workbook contains several tabs (for example SOP, Exam Schedule, Server Room Threshold), the required tab must be placed first or saved as a separate file.
  • Row 1 holds the headers, except in File 2, whose template has the title Exam Schedule in row 1 and the headers in row 2.
  • TC codes are text, written identically in every file (for example 50106, with no trailing .0).
  • All times must be in 24-hour format (13:30, not 01:30).
  • Schedule, threshold and recipient uploads display a preview first. Errors prevent saving and are listed by row; no upload is partially saved.
Layouts that cannot be processed The layouts below cannot be read automatically. CDIS can transcribe them manually, but this adds time and the risk of transcription error. Please submit the layouts specified in this guide.
  • Dates across, shifts below. A schedule laid out horizontally (Date | 17th Sept | | | 18th Sept followed by Shifts | Shift 1 | Shift 2 | Shift 3). Use one row per date instead (File 2).
  • Two header rows. Threshold or schedule matrices with the date on one row and S1 S2 S3 on the next. Combine them into a single header such as 17-9-26 Shift 1.
  • Contact lists without a TC code. A list such as Sr No | Contact Number. See File 6 for the two accepted ways to supply numbers.
  • Times without AM/PM or with a dot separator. Examples: 01:30:00 meaning 1:30 PM, or 4.30 AM. Write 13:30 and 04:30.

File 2Date and shift schedule

RTSPHLSRequired

One row per examination date and one column per shift, with Yes or No in each cell. A slot marked No, or a date that is absent from the sheet, means the examination does not run and nothing is monitored. This schedule always takes precedence over the centre-wise schedule.

  • Row 1 contains the title Exam Schedule. Row 2 contains the headers: Sr.No., Date, and one Shift N (HH:MM:SS to HH:MM:SS) column per shift.
  • Date format: 30-Sep-26 (day, three-letter month, two-digit year). Each date appears once.
  • Cell values: exactly Yes or No.
  • "Shift N" corresponds to the Nth shift of the examination, so the shift order in File 1 must agree with this sheet.
  • The sheet must be the first tab of the workbook, or a separate file.
Verify afternoon timesSource documents frequently show Shift 2 (01:30:00 to 02:30:00) and Shift 3 (05:00:00 to 06:00:00) where 13:30 and 17:00 are intended. The system raises a warning for any time before 06:00; if uncorrected, the night-time hours would be stored as the shift. Enter 13:30:00 and 17:00:00.

File 3Centre-wise schedule

RTSP · requiredHLS · recommended

One row per centre and one column per date and shift, with YES or NO in each cell. In each slot only the centres marked YES are classified and monitored. A centre with cameras that is missing from this sheet is not monitored on any date. For HLS examinations the camera sheets already list cameras per shift and date; this schedule additionally excludes centres from the slots in which they do not participate.

  • Row 1 contains the headers: TC CODE, followed by one column per date and shift. No other columns are required.
  • Date and shift header format: d-m-yy Shift n, with single spaces, for example 30-9-26 Shift 1. Include one column for every date and shift of the examination; each combination appears once.
  • Cell values: exactly YES or NO. An empty cell is treated as NO with a warning.
  • One row per centre; each TC code appears once, and every centre that has cameras must be listed.

File 4Camera list

RTSPHLSRequired

RTSP  One file for the whole examination

  • Row 1 contains the headers exactly as shown: Device ID, Camera No, TC Code, Camera Name, Centre Name, City, State, Region, CCTV URL.
  • Device ID is the DVR identifier. Camera No is the channel on that DVR, starting at 0. CCTV URL is the DVR server host, for example dvr01.example.com, or a full rtsp:// or http(s):// URL.
  • Device ID and CCTV URL are mandatory. A row without a Device ID or CCTV URL is skipped. A row whose CCTV URL is not a valid server address (for example "New" or "Updated") is not imported and is listed in the upload message.
  • A camera is identified by Device ID + Camera No + TC Code. Uploading a camera that already exists updates only its Classification and Region; its server, name and centre details are not changed. To correct these, or to remove cameras from the list, inform CDIS. A camera repeated within one sheet is kept once.
  • Region is optional and enables filtering of the Cameras and Detections pages by region. It must contain a region code, not a server address.
  • Optional extra column Classification: if the view of a camera is already known, enter one of Computer Lab, Server Room, Entry, Outside Area, Biometric Area. If the column is omitted, the AI assigns the view.
  • Camera Name should describe the location, for example LAB1 CAM4, BIOMETRIC AREA, CORRIDOR AREA or SERVER ROOM.
  • A full examination may contain about 3,100 cameras. If a file exceeds 10 MB, split it into several files.
  • The DVR login for CDIS must be active and reachable from CDIS servers before the first examination day. Please state the number of simultaneous sessions each DVR permits.

HLS  One sheet per shift, for each exam date

  • Row 1 contains the headers exactly as shown: S.No., TC Code, Centre Name, City, State, LIS IF/IDZ, LAN and Lab Name, Camera Name, CCTV URL, ch_no, Camera Category.
  • CCTV URL is the camera stream link from the client's CCTV portal, typically a portal page link (for example https://portal.example.com/cctv/stream?centre=…&camera=…) that resolves to an .m3u8 playlist. ch_no is the unique channel key of the camera. A row missing either value is skipped.
  • The shift and date are selected at the time of upload. Supply one sheet per shift (Shift 1, Shift 2, Shift 3) for each exam date. The centres and cameras may differ from shift to shift, and the date must be an examination date.
  • List each camera once per sheet. ch_no must be unique within a sheet; for a repeated ch_no only the first row is kept and the remaining rows are discarded with a message.
  • Camera Category must be exactly one of Inside Lab, Outside Lab, Entry/Exit or Server Room, and must be completed for every camera. Other spellings (for example Outside, Outside Room or Entry/Exit Gate) are accepted at upload but are not recognised, and the camera is then assigned by the AI label instead. Where an analytic is restricted to certain camera types, this column takes precedence over the AI label. In the analytics plan (File 7), the Camera Type Outside applies to cameras with the category Outside Lab; the other three names are the same in both files.
  • LAN and Lab Name and LIS IF/IDZ are informational and may be blank for outside cameras (for example OUTSIDE_ROOM_CCTV). An optional extra Classification column overrides the AI label when present.
  • Links must remain valid for the entire shift window. Short-lived or time-restricted links are the most common cause of cameras appearing as Not Accessible.
  • Re-uploading a sheet for a shift and date that is already loaded adds new cameras but does not replace the links of existing ones. If links change, for example refreshed or time-limited links, inform CDIS so that the sheet for that shift and date can be replaced.

File 5Server room limits

RTSPHLSIf applicable

The maximum number of people permitted in each centre's server room. An alert is raised when the number of people observed is greater than the limit.

  • Row 1 contains the headers TC CODE and Maximum Server Room Threshold. No other columns are required. One row per centre.
  • Fractional values are rounded to the nearest whole person (7.75 becomes 8), and a limit of 0 is skipped.
  • Once this file is uploaded for the examination, a centre with no row receives no server room alerts, and limits from other examinations are not used. If the file is not supplied, limits previously held by CDIS for a TC code may apply, so submit this file whenever server room monitoring is required.

Limits that vary by date and shift

If the limit differs between sittings, replace Maximum Server Room Threshold with one column per date and shift, using the header format of File 3. Keep a single header row.

  • Cell values are whole numbers. 0, NA or an empty cell means the centre is not scheduled in that slot.
Threshold semanticsThe alert is raised when the headcount is greater than the limit (a limit of 4 alerts at 5 people). If the SOP states "equal to or more than the limit", supply the highest permitted headcount as the limit, or inform CDIS so that both sides interpret the figure identically.

File 6SMS recipients and templates

RTSPHLSIf SMS used

When the client accepts an alert on the dashboard, an SMS is sent. The recipients can be defined in either of two ways.

Option A · recipients per centre

Two columns, TC Code and Mobile Number. The SMS is sent to the numbers listed for the centre of the alert.

Option B · one list for all centres

A plain list of mobile numbers (for example Sr No | Contact Number) for a central team. CDIS enters it against the examination and every alert is sent to these numbers. This list must not be uploaded as a per-centre file: without a TC code column, the first column would be read as the TC code.

For each alert the recipients are resolved in this order: the centre's numbers (Option A), then the examination-wide list (Option B), then the default recipients registered for the client's company.

  • Row 1 contains the headers exactly as shown: TC Code and Mobile Number.
  • One number per row, repeating the TC code for each additional number. Numbers are 10-digit mobile numbers without country code, spaces or dashes.
  • Each upload replaces the entire per-centre list, so every upload must contain the complete list.
  • Alerts are delivered by SMS only; email lists are not used for alerts.
  • SMS is available for: invigilator (including crowd below 5 with invigilator static), proximity, server room, intruder, entry crowd, phone, entry/exit and blind spot.
  • An alert type is sent by SMS only after its DLT template has been registered for your organisation. Templates are held per client organisation, so all examinations of one client use the same templates.

SMS templates (DLT)

Indian telecom regulations require each message body to match a template approved on the DLT portal. For every alert to be sent by SMS, provide the following five items.

File 7Analytics plan (SOP)

RTSPHLSRequired

The client's SOP table serves as the analytics plan and may be submitted as it stands, subject to the points below. CDIS enters each row on the scheduling screen. The expected layout has one row per analytic and camera type, with a Start and End pair under each shift.

SOP documents usually place "Shift 1 / Shift 2 / Shift 3" on a merged row above "Start time / End time". The grid above shows them combined in a single header for display.

  • Camera Type must be one of Inside Lab, Server Room, Entry/Exit or Outside. For HLS examinations only these four may be used: each corresponds to a Camera Category in the camera sheet, with Outside covering cameras of category Outside Lab. For RTSP examinations, Computer Lab, Inside Classroom, Strong Room and Biometric may also be used. Use one row per analytic and camera type, as in the Crowd and Phone rows above, so that each row can carry its own time window and SMS setting.
  • Start and End per shift are 24-hour times in the form HH:MM, with the End after the Start. A dash indicates that the analytic does not run in that shift. A window may begin before the examination starts (intruder checks commonly do) and may differ for each analytic.
  • Alert gap (seconds) is the minimum interval between two alerts from the same camera for that analytic, entered as a whole number of seconds (for example 120 for 2 minutes). Leave it blank to use the platform default for the analytic.
  • SMS to observer is Yes or No for each row. Yes is effective only for the analytics listed in File 6 and requires a template and recipients.
  • Alert thresholds, such as "10 or more people", "7 minutes without movement" or "any phone", are applied by the platform and are recorded in the SOP for reference. The server room limit is the exception and is supplied in File 5.
  • If the same analytic runs on different camera types within one shift, offset the start of the second row by one minute (see the Phone rows above).
Use 24-hour times12-hour times are the most frequent source of error in SOP documents. Shift 2 is often written as 01:30:00 to 02:30:00 and Shift 3 as 05:00:00 to 06:00:00 (meaning 13:30 and 17:00), or times appear as 4.30 AM and 2.00 PM. Convert every time to HH:MM in 24-hour form before submission.

5Conducting the examination

Client dashboard

  • Dashboard: examinations by status (Scheduled, Ongoing, Completed), cameras Accessible versus Not Accessible, detections Pending, Accepted and Removed, and the analytics running that day.
  • Cameras: every camera with TC code, centre, category, classification and status, filterable by shift and exam date. "Open frame" displays the snapshot used for classification.
  • Detections: live feed with the annotated snapshot, camera, centre, TC code, shift and time, filterable by date, type, centre or city.
  • Video Uploads: images and videos organised by TC code.

Handling alerts

  • Accept confirms that an alert is valid. The SMS to the designated observers is then sent automatically using the registered DLT template.
  • Remove dismisses a false positive from the active feed. The detection remains on the Removed Detections page and can be restored.
  • No detection is deleted. Accepted and removed decisions are reflected in the shift report.

Reports

  • The per-shift Excel report contains cameras with channel ID and status, event counts, and a Detections List with Status (Accepted, Rejected or Not Verified) and a link to each image.
  • Cameras of centres that do not participate in a slot are left out of that shift's camera counts, so they are not reported as offline.

Client responsibilities on the day

  • Keep DVRs powered and stream links valid for the whole shift.
  • Notify CDIS promptly of any camera relocation, centre cancellation or change in shift timing.
  • Review Not Accessible cameras with the centre, since a camera that cannot be opened cannot be analysed.

6Portal access

  • Each user registers with name, email, mobile number and company, and verifies the account with a one-time password (OTP) sent by email or SMS.
  • A CDIS administrator then verifies the account and assigns the client (viewer) role. Verification is performed manually, so users should register before the examination week.
  • Access is granted per examination. After verification, CDIS assigns each user to the examinations for which they are listed. A user sees an examination, with its cameras and detections, on the client dashboard only after being assigned to it. A user must have registered and been verified before they can be assigned.
  • For every new examination, please send the list of users who should have client dashboard access to it, with each user's full name, email address, mobile number and company. Access to earlier examinations does not carry over, so include existing users again if they also need the new examination.
  • A user who works for several companies can hold several memberships under a single login.
